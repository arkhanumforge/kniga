# Архитектура RAG для книги

Статус: технический проект этапа 1.5, 2026-11-27. Не действующая инструкция писателю и не изменение канона. Реализация — этап 7, приёмка — этап 8. Входная версия: `c84be5864555fa6fb86f73000a8c51941a451ffd` (docs-revision). Результаты этапа 1 сохраняются. [План ревизии](<План ревизии.md>) · [Журнал](<Журнал ревизии.md>).

## 1. Решение и границы

RAG здесь — извлечение необходимой информации из репозитория перед работой над текстом. Выбираем гибрид из трёх слоёв, а не поиск по похожим словам вместо чтения:

1. **Обязательное ядро**: маршрут и приоритеты (AGENTS, GENERAL после этапа 7), правила непротиворечивости, полный рабочий «Стиль.md» при художественной работе; нужные правила и навык. Включается независимо от запроса и рейтинга поиска. В стиле сохраняются полноценная рефлексия, реальное время мысли, голос, физика, отношения и две вычитки; примеры извлекаются по ссылкам. Справочник не заменяет ядро, карта аудита не инструкция.
2. **Детерминированный срез**: версия, вход в сцену, состояния, хронология, все четыре карты знаний, прошлый опыт, полные актуальные портреты Лизы и существенных героев, соответствующие отношения и механики мира. Срез формируется по идентификаторам и времени, а не по top-k. В начале реализации — полное чтение четырёх карт, пока тесты не докажут полноту более компактного среза.
3. **Поисковое дополнение**: ранние эпизоды, исключения лора, точные формулировки, примеры стиля, связанные закладки. Выдача с источником, версией и координатами; открывать первоисточник и необходимые соседние абзацы. Пустой результат означает отсутствие совпадений, не отсутствие факта.

Базовый режим — обычные Markdown, структурированные разделы и прямые ссылки в GitHub. Он не требует ПК, API-ключей, внешнего сервера или установки приложений. Автоматизированный индекс производный и необязательный. Ни один поиск не решает за автора содержательные споры. Не сокращаем текст инструкций и рефлексию ради метрик.

## 3. Модель данных и структура Markdown

Источник истины — редактируемый Markdown, не индекс, не отдельная вручную заполняемая база фактов. В этапах 2–5 вводим заголовки со стабильными ID там, где нужны точные связи. Можно использовать машиночитаемый HTML-комментарий непосредственно после заголовка или таблицу/строку с ID и явными колонками. Комментарий не должен быть единственным способом увидеть смысл: статус и временная граница видны и человеку. Метаданные наследуются от раздела только если применимы ко всему блоку; отдельная строка/подраздел переопределяет их. Смешанный статус разбивается. Формат ниже — проект, не обязательство массово переписать Markdown сейчас.

| Поле | Смысл |
|---|---|
| id | Устойчивый ID факта/правила/записи, например K-LIZ-008-004; при переносе ID остаётся. Не номер строки и не хеш текста. Для старых неподготовленных фрагментов временный ID с blob, пометка «непроверен». |
| source | Путь, полный путь заголовков, ID/якорь, диапазон строк, blob SHA; provenance содержит ссылку на первичную сцену, авторское решение либо норму. |
| kind | rule, character, relation, world, knowledge, event, state, plan, example, open_question, audit, process. |
| subject / tags | О ком/о чём факт (например, пленник, кровь, сон); контролируемые идентификаторы сущностей и алиасы. |
| holder / audience | Кто действительно знает: liz, pascal, rainor, reader или иной герой. Для объективного лора holder=author; область применения механики не равна знанию о ней. |
| timeline | Книга, глава, сцена, порядковое событие внутри сцены; границы valid_from/valid_until для меняющегося состояния; learned_at для раскрытия; при пробеле — unknown. Время события и получения сведений могут различаться. |
| version | Идентификатор линии (mainline, alternative:<id>), точка развилки, источник принятия; ветка/commit/blob фиксируют техническую версию, но не заменяют статус принятия. |
| status | accepted, planned, proposed, alternative, example, disputed, superseded, unknown. Раздельно: утверждённый приём/правило и ещё не произошедшее событие. |
| epistemic | observation, report, inference, belief, uncertainty, author_truth; отдельно confidence для субъекта (подозрение, сильная гипотеза, уверенность, подтверждено) и author_assessment (верно/частично/ложно/неизвестно). Намеренная ложь и чужой рассказ требуют источника и адресата, не превращаются в объективную истину. |
| links | requires (условия и исключения), evidence (эпизод), supersedes (изменение состояния/гипотезы), transfer (кто, кому, когда, что передал), related (смысловая связь); ссылки по ID и при необходимости точный путь. |

Минимум для всех блоков: id, source, kind, status, version, subject/tags; holder, learned_at, confidence обязательны для знаний; временные границы — для состояний и фаз; evidence и requires — для выводов и зависимых условий. Нет выдуманных дат, нет автоматического присвоения accepted из имени файла. Значение unknown приводит к ручной сверке, а не к разрешению на раскрытие. Сохраняем прежние ступени, включая отвергнутые гипотезы.

Пример формы (иллюстрация схемы, не новая каноническая запись):

```yaml
id: K-LIZ-EXAMPLE
kind: knowledge
subject: nature_of_rainor
holder: liz
version: mainline
status: accepted
learned_at: {book: 1, chapter: 8, scene: unknown, event: unknown}
epistemic: inference
confidence: suspicion
author_assessment: separate
evidence: ["Знания Лизы.md: уточнение о реплике Райнора"]
links: {requires: [], supersedes: [], transfer: []}
```

В этом примере accepted означает, что подозрение зафиксировано в основной карте, а не подтверждение природы Райнора. Точная сцена проверяется на этапе 4. В рабочем индексе строку с unknown нельзя использовать как подтверждение знания в более ранней точке.

Разбиение: H1–H6, явные ID, смысловые абзацы, таблицы вместе с шапкой, связанные примеры и подписи, списки условий вместе с нормой и исключениями. Не дробить пары «плохо/лучше», диалог или причинную цепь по произвольному числу символов. Большие разделы получают дочерние фрагменты с сохранёнными заголовками и ссылкой на родителя; при загрузке подтягиваются соседние абзацы и requires. Ориентир на 300–800 слов для поискового фрагмента, не квота; важное правило может быть коротким, сложная механика длинной. Служебные комментарии разбираются отдельно. Фрагменты не обрезаются молча; для слишком большого блока возвращается диапазон чтения.

## 4. Разделение версий, времени и доступа

До подготовки агент фиксирует манифест запроса: branch/ref SHA, выбранная линия и файл, сцена/последнее действие на входе, цель (план/текст/правка/brainstorm/закрытие), POV, существенные участники и читатель. В сцене с изменением знаний — отдельные границы до и после передачи. Если новая версия переписывает сцену, вход остаётся до развилки; выводы удаляемой сцены недоступны. Статус утверждения проверяется по авторскому выбору, а не времени коммита.

Предлагаемый реестр версий на этапе 5: глава 1 — соответствующая часть Книга.md, главы 2–8 — отдельные утверждённые файлы по действующим GENERAL/картам; Глава 8.1.md, Глава 8.3.md и черновики главы 9 — только отдельно по явно выбранной версии. Точное принятие подтвердить в этапах 4–5; не решаем открытый вопрос сейчас. Книга.md как дублирующий источник исключается из общего поиска, но диапазон главы 1 нужен; не исключать его целиком, не включать обе копии. Планы 8–10, арки, План лора и будущие разделы карт — область планирования, не свидетельства случившегося. Аудиты, журнал, черновики, архив, raw, изображения, отзывы — исключить из выдачи писателя по умолчанию, сохранять доступ для аудита/по прямому запросу. Шпаргалка долгов — отдельный тип закладки, с состоянием «открыта/реализована» и проверкой источника.

Два разных представления (даже если один агент исполняет обе роли):

- **Авторское**: принятые объективные законы, скрытые мотивы, планы отдельно с маркировкой статуса, карты всех участников, пределы того, что позволено вывести в текст. Нужно для планирования и проверки физической причинности. Не считать доступное автору доступным герою.
- **POV/реплики**: только разрешённые на входе знания соответствующего субъекта, включая его ошибки и степень уверенности, наблюдения сцены и явные передачи в ней. Для повествования от Лизы отдельно её карта и читательский срез; после скачка не склеивать. Для реплики Паскаля или Райнора — только их индивидуальные карты, в том числе когда общий фонд расходится. Авторский лор можно применить для физики, но нельзя автоматически назвать в тексте. Читатель может интерпретировать увиденное, не имеет доступа к чужим мыслям.

Фильтрация выполняется **до ранжирования**: допустимая линия и ветка/commit → статус/тип → интервал времени → holder/audience → запрос. План и гипотезу допускаем только в предусмотренной области с явным ярлыком; скрытое не выводить даже в превью, заголовок, объяснение связи или алиас. Общая предметная база мужчин — отдельные подтверждённые записи/ссылки каждого, не автоматическое объединение карт. Не путать внутреннюю уверенность Лизы с оценкой автора. Для проверки намеренной лжи героя источник — его цель/знание и доступные наблюдения собеседника; не маскировать пробел в каноне ложью.

Это логическая граница выдачи, не криптографическая защита от спойлеров: если весь авторский контекст уже загружен в тот же агент, фильтр не заставляет модель забыть его. В идеале отдельная подготовка POV-пакета и независимая авторская проверка. В телефоне возможны раздельные сообщения/контексты или явное разделение пакетов; в любом случае ручная проверка каждого существенного знания обязательна. Нельзя гарантировать ноль ошибок модели.

## 5. Детерминированный маршрут подготовки

1. Закрепить commit и точку входа, сверить статус рукописи; открыть последнюю принятую сцену и достаточный контекст до неё. Не брать «Сейчас» конца 7 как состояние конца 8. При расхождении сводок открыть первичную сцену; при неясном принятии версии — вопрос автору.
2. Загрузить обязательное ядро и действующие правила. До завершения этапа 7 соблюдать действующее требование чтения карт и карточек, не заменять его данным проектом.
3. Собрать четыре независимых среза: записи до границы (включая ранние неизменившиеся), последнюю ступень каждого изменяющегося знания, историю смены гипотезы и незакрытые вопросы, явные запреты/границы раскрытия. Для участников вне четырёх карт взять их индивидуальные свидетельства и историю, не придумывать сведений. Не отбирать только по сценическому составу. Если структурированность/покрытие не доказаны, читать четыре карты целиком по разделам и вручную отсекать будущее; сравнивать с рукописью.
4. Загрузить полный актуальный блок Лизы и важных героев (биография, опыт, мотивы, голос, телесность, отношения, текущая фаза). Разделы арок в карточках отделить от прошедшего. Для диалога открыть соответствующую пару и фазу из «Химии»/отношений; разницу между намерением, заботой, страхом, притяжением и доверием не сглаживать. Фаза определяется событиями, не номером будущего этапа.
5. Собрать state/experience: кто где, оковы, предметы, голод/раны, позы, свидетели, цель, что каждый пережил и вынес; поднять ранние поступки, обещания, причинённый вред, прежние попытки и их цену. По каждому планируемому решению/мысли спросить, какой прежний опыт опровергает удобную реплику. Например, запрос о самооценке Лизы должен вести не только к финалу 8, но и к причинённому ею вреду в ранних главах. Проверить источник и доступность опыта говорящему.
6. По субъектам, механикам, условиям и предполагаемым действиям пройти связи requires/evidence, открыть правила мира со всеми исключениями. Составить матрицу обязательных проверок (вход, участники, знание/свидетель, опыт, тело, лор, отношения, стиль, план, закладки). У механики есть активирующие условия и последствия, даже когда сцена о другом. При отсутствии явной ссылки искать вручную по навигации и синонимам; при неполноте — не объявлять контекст достаточным.
7. Поиск дополнительно поднимает подробные разборы, улики и исключения. Проверить первоисточники. Внутренний короткий паспорт подготовки содержит выбранную версию, точку, список источников/диапазонов, статус покрытия каждого обязательного блока, конфликты и пробелы. Не хранить второй пересказ канона. Перед художественным текстом — цели, эмоции, тактики, физика и динамика знания; после — логическая проверка, отдельная художественная вычитка, повторная сверка изменённых действий/знаний, стыков и повторов.

Маршруты отличаются: план и существенная правка — тот же канонический фундамент + открытые решения; написание — дополнительно ядро стиля и соседняя проза; чистая грамматика — свежая версия и стык, без смысловой правки; стилистическая правка — ядро, эталон и проверка неизменности смысла, при изменении мотива/знания — полный маршрут; brainstorm — авторская область с ярлыками, не превращать идеи в факты; закрытие — после принятия сцены пересчитать четыре карты, состояния и зависимые эпизоды, обновить индекс. Не автоматически писать или коммитить рукопись.

## 6. Лексический и семантический поиск

Первая автоматизация (после 6): локальный индекс JSON или SQLite, явный список активных источников и диапазонов, фильтр из §4, детерминированный слой отдельно. Лексика: Unicode NFKC, нижний регистр, нормализация ё/е и ударений при поиске (не менять оригинал), морфология русских словоформ через локальный словарь/лемматизатор, при отсутствии зависимостей — точные слова + осторожные символьные n-граммы/варианты запросов. BM25 или эквивалент с частотой по корпусу и длиной, вес заголовка/ID, точные имена/фразы, объединение запросов. Алиасы в одном небольшом реестре сущностей, например Элизабет/Лиза/Лиззи, Райнор/Райнер, Паскаль/Паск; «Кривой»/«пленник» — поисковый alias для автора, не разрешение назвать его так в POV. Не склеивать разных героев по похожему имени. Порог, top-k и словарь настраиваются тестами, не заменяют обязательную выдачу.

При наличии ресурсов — локальная мультиязычная embedding-модель для смысла («почему она считает себя опасной» ↔ ранние поступки) с известной версией и лицензией, русскоязычные тесты. Применять одинаковые фильтры до/при выборе кандидатов; объединять ранги лексики и семантики (например, RRF), исключать дубликаты по ID, расширять связи и возвращать родителя/условия. Если embeddings недоступны, лексика + структура/ссылки остаются рабочим решением. Не отправлять рукопись в сторонний API без отдельного согласия. Не требуется векторная БД для небольшой книги.

Выдача содержит score только для кандидатов, а также id, тип, статус, субъект, точку, источник, commit, строки, причину включения (обязательное/связь/поиск), открываемую ссылку на blob этого commit с диапазоном. Превью не считается прочитанным правилом. Ранжирование не должно вытеснять ни одно обязательное условие. Контроль полноты идёт по карте покрытий, а не числу найденных совпадений.

## 8. Версионирование и обновление

Все чтения одной подготовки привязаны к одному commit. Манифест индекса: source_commit, source_branch (для диагностики), schema_version, generator_version, hashes/blob SHA всех входных файлов, список диапазонов/версий, параметры нормализации и версия embedding при наличии. Для генерируемого указателя в новом коммите источник — родительский commit и набор хешей документов; сравнивать входные blob с текущей версией, иначе собственный коммит указателя сделает его «устаревшим» бесконечно. Любой изменённый релевантный blob, удаление, новый принятый текст, смена статуса/схемы или расхождение линии требует перестроения затронутых записей и зависимостей; при сомнениях полный rebuild. Индекс не канон и не источник принятия главы.

После авторского утверждения сцены: обновить текст (только с разрешением), пересчитать передачи/изменения гипотез всех четырёх карт, состояния, прошлый опыт, связи и закладки; при изменении ранней главы — все зависимые поздние записи. Проверить ссылки и статус версий, построить производный индекс из одного согласованного снимка, затем проверить freshness. Не автоматически переносить черновики в основную линию. Пока синхронизация не выполнена, актуальный утверждённый текст имеет приоритет для произошедшего и раскрытия, не для выдумывания нового объективного правила мира. При сомнении — зафиксировать спор.

Fallback: проверить SHA/статус, перечитать обязательные файлы по диапазонам, пройти оглавления, прямые ссылки и первичный эпизод. Если коннектор обрезал выдачу — разбить на меньшие диапазоны, проверить начало, конец и перекрытие, фиксировать пропуски. Если файл недоступен/спор не разрешён — назвать конкретный блокер, не объявлять готовность сцены и не угадывать канон. Новая авторская правка во время подготовки требует повторной проверки изменившихся источников. Никакого тихого перехода на main или backup.

## 10. Критерии приёмки и контрольные задачи

Сначала эталон обязательных фактов/границ для каждой тестовой точки строится вручную по принятому тексту и профильным источникам (этап 6). Не выдавать тестируемому писателю правильные ответы. Включить раннюю, среднюю и текущую главу, начало и конец одной сцены, альтернативную версию, удалённую реплику, неразрешённый факт, смену фазы. Проверить запросы на разных словоформах и неявных формулировках. Для будущих развилок до написания — синтетические записи с маркировкой test, не канон.

| Случай | Что проверяет |
|---|---|
| «Как её звать пленника?» / «Она знает его имя?» до раскрытия | Алиас для поиска, не имя в POV. Ссылка на стиль и карту; не подсунуть биографию из плана. |
| «Кто из мужчин догробник?», до и после вырезанной реплики | Объективная истина отдельно; Лиза/читатель не получают удалённое подтверждение; версия и граница важнее score. |
| «Почему она опасна даже если не хотела причинить вред?» | Ранний опыт укуса/раны, последующие события, один эпизод контроля не гарантия. Не повторять готовую улику как новую; проверить соответствующие главы. |
| «Что значит, что пленник смотрел на хлеб?» | Наблюдение и предположение, не доказательство тяги к пустой руке; вернуть условие, исключение и нужные эпизоды. |
| «Что Паскаль узнал из разговора и о чём Лиза только подумала?» | Передача и отсутствие передачи; отдельно читатель и Паскаль. |
| «Кровь, плоть, сон, память, Внушение» | Полные правила и исключения; авторский механизм не даёт героям раннее знание. |
| «Почему Паскаль продолжает уход, если Райнор вернётся?» | Портрет, профессиональная задача, избегание конфликта не страх; химия и актуальная стадия; не механический пересказ правил. |
| «Начало 8 / конец 8 / новая редакция 8 / третий сон» | Разные срезы тела и пространства, прежняя точка входа, исключение альтернатив и плана; отсутствие будущего раскрытия. |
| «Лиза после скачка», «мужчины после ссоры» | На синтетическом/плановом наборе проверить независимость четырёх карт, отдельное получение и раскрытие; не представлять будущие события как уже случившиеся. |
| Исправление ранней записи, удалённый файл, смена commit, потерянная ссылка, длинный ответ | Индекс признаёт устаревание, пересчёт зависимостей, точный fallback без молчаливого пропуска. |
| Учебный диалог о ноге, пример из альтернативы и поздняя арка | Не становятся событиями; разбор пригоден для стиля, ссылка на правильную версию. |

Метрики (проектные пороги, не измеренные результаты):

- **Обязательное покрытие:** найдено/нужно = 100% по ручному эталону на каждой контрольной точке, включая ранние факты и зависимости; ни один обязательный блок не вытеснен top-k. Если не достигнуто — не отменять полное чтение карт/карточек.
- **Утечки:** 0 будущих, чужих или альтернативных фактов как разрешённых знаний в POV/репликах и выдаче reader; 0 примеров/планов, представленных как случившиеся. Проверять также превью и родительские фрагменты. Не считать тестовую выборку гарантией поведения модели.
- **Точность источника:** 100% обязательных записей имеют рабочий ID/ссылку/диапазон того commit, который действительно подтверждает утверждение. Отдельно проверять точность смысла и статус принятия. Ошибочная ссылка — провал даже при верном ответе.
- **Поиск:** recall@10 и precision@10 по дополнительным релевантным фрагментам, отдельно ранжирование лексики и гибрида; начальный ориентир recall@10 ≥ 0,9, без послабления для обязательных фактов. Если эталон требует более 10 фрагментов, проверять расширенную выдачу/связи; не искусственно ограничивать.
- **Нагрузка:** измерять символы, слова, число вызовов, время, размер каждого пакета; токены только по реальному токенизатору либо явно описанной оценке. Сравнить со старым маршрутом при одинаковой сцене. Ориентир 20–35 тыс. токенов подготовки из плана — исследовательская цель, не лимит; сохранить запас для рассуждения и текста. Не обрезать обязательные источники.
- **Художественный результат:** независимые черновики одинаковой сцены/плана в сопоставимых моделях и свежих контекстах; слепая оценка автором/проверяющим по лору, знаниям, памяти, физике, мотивации, голосу, глубине мысли, химии, повторам и ясности кадра. Отдельно логические нарушения (неприемлемы) и художественные оценки (не хуже старого маршрута, желательно лучше). При ухудшении не объявлять победу на основании меньшего контекста.

A считается пригодным после реального прохода через GitHub с телефона без запуска локального скрипта и с проверенными источниками; B/C отдельно после подтверждённого исполнения, обновления и чтения. До этого проект принят только как архитектура, не как работоспособная реализация. Если новая система не доказывает полноту — продолжаем полное чтение обязательных документов, исправляем структурирование, не ослабляем требования.
